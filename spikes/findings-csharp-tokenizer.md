# C# のトークナイザで Ruri v3 と同じトークン ID が出るか

Windows 版（C#）に意味の層を入れられるかの分かれ目。
**食い違っても例外は出ず、黙って違うベクトルが出る**ので、使ってみて気付くことができない
（spec-local-ai.md 4.6）。既製品で足りるなら自前実装を持たずに済む。

測ったのは `Microsoft.ML.Tokenizers` 2.0.0 の `SentencePieceTokenizer`。
照合の相手は macOS 版の検査が使っている凍結済みの期待値 37 件
（`macos/Tests/ChoroReaderTests/Fixtures/ruri-v3-tokenizer.json`、kohagi = Rust の
tokenizers crate で 1 度作ったもの。例文は架空で、実在の書籍からは取っていない）。

harness は `spikes/csharp-tokenizer`。macOS でそのまま走る（純粋な .NET なので Windows は要らない）。

## 結果

**同じ ID は出ない。**

| | 一致 |
|---|---|
| 素のまま | 24 / 37 |
| 特殊トークンを渡す | **31 / 37** |

**読むファイルが macOS 版と違う。** あちらは `tokenizer.json`（HuggingFace の形、6.4 MB）で、
`Microsoft.ML.Tokenizers` が読むのは `tokenizer.model`（SentencePiece の protobuf、1.8 MB）。
同じモデルの配り物だが別のファイルである。

残った 6 件は 3 種類に分かれ、**性質が違う**。

### 1. 空文字で何も返さない（1 件）

期待は `[1, 2]`（bos と eos だけ）、C# は `[]`。
呼ぶ側で弾けばよく、順位に関わらない。

### 2. byte fallback の id が +255 ずれる（4 件）

語彙に無い字は `<0xXX>` に落ちる。その並び先が両者で違う。

| | `<0x00>` の位置 |
|---|---|
| 期待（tokenizer.json） | 15 |
| C#（tokenizer.model） | 270 |

改行・絵文字・稀な漢字がここに当たる。**ずれは 4 件とも一定で +255**。
対応表を挟めば揃うが、他人の実装の中身に合わせて外から補正することになる。

### 3. 同点の分け方の採り方が違う（1 件）

これが効いた。罫線の連なり（`──────…`）で、

```text
期待: 15425, 91907, 49793, 49793, 49793
C#  : 49793, 49793, 91907, 15425, 49793
```

**長さも、使っている語彙の中身も同じで、並べ方だけが違う。**
点が同じ分け方が複数あるときにどれを採るかが違う。

これは `findings-swift-tokenizer.md` で Swift 実装が踏んだ 3 つ目とまったく同じ形である。
あちらは「同点は開始位置の小さい方（長い語彙）を採る。バイト位置を昇順に進め、
等号を含まない比較で更新すれば参照と同じになる」で揃えた。
**Viterbi の中の話なので、外からは直せない。**

目次の点線、罫線、区切りの連なりは技術書の本文に普通に出る。
段落単位の索引（spec-local-ai.md 4.1）ではそういう段落が丸ごと別のベクトルになる。

## 速さ

トークナイズそのものは問題にならない。

| | |
|---|---|
| 400 字 1 段落（189 トークン） | **0.048 ms** |

1 冊 580 段落でも 28 ms である。値段を払うのは推論の側で、ここではない。

## 判断

**`Microsoft.ML.Tokenizers` は使わない。Swift 実装を C# へ移す。**

- 1 と 2 は補正できるが、**3 は補正できない**。1 つでも残るなら防壁にならない
- 移す先は `tokenizer.json`（macOS 版と同じファイル）にする。
  配り物を 1 種類に保てるし、照合の相手も同じものになる
- 元は 259 行で、踏む所は 3 つとも `findings-swift-tokenizer.md` に書いてある。
  凍結済みの期待値 37 件がそのまま検査になる。**書く量より、書いたものを確かめる手立ての方が揃っている**
- C# の `string` は序数で比べるので Swift の正準等価の罠（1 つ目）は出にくいが、
  同じ理由でバイト列で持つ。点の足し込みは `double` で行う（2 つ目）

harness はそのまま残す。移した実装を同じ 37 件に通せば、既製品と並べて比べられる。

## 移した結果

`windows/ChoroReader.Core/UnigramTokenizer.cs`（約 370 行）。**37 件すべて一致した。**

| | 一致 |
|---|---|
| `Microsoft.ML.Tokenizers`（素） | 24 / 37 |
| `Microsoft.ML.Tokenizers`（特殊トークンを渡す） | 31 / 37 |
| **移した実装** | **37 / 37** |

3 つの罠は 4 通りに壊して、検査が噛むことを見た。

| 壊し方 | 落ちる検査 |
|---|---|
| 同点で後から来た方を採る（`>` を `>=` に） | 同点なら長い語彙を採る／参照実装と同じ ID |
| 点を float で積む | 点は double で積む／参照実装と同じ ID |
| 語彙を NFC に正規化して読む | 濁点の形が違えば別の語彙／参照実装と同じ ID |
| byte fallback をやめる | 語彙に無い文字はバイトに落とす／参照実装と同じ ID |

**37 件の検査は CI では飛ぶ。** そこに寄りかかると CI では誰も確かめていないことになるので、
**3 つの罠は合成した語彙でも噛むようにした**（上の表の左列は、本物の語彙が無い状態でも落ちる）。
本物が無いときは `Skipped: 1` と出る。

**追記。** `choro-convert --format onnx` は `tokenizer.json` を変換物のそばへ写す
（[findings-csharp-embedder.md](findings-csharp-embedder.md)）。
そちらの 6.4 MB でも同じ 37 件が通ることを確かめた。
