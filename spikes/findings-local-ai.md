# スパイクの結果：日本語技術書での意味検索の品質

spikes/local-ai-embedding.md を実施した。判定は **NO-GO（保留）**。

OS が配る埋め込みモデルでは、関連箇所も意味検索も実用の品質に届かない。
原因は特定できており、モデルの選び方の問題である。使えるモデルを持てるなら道は残る。

実蔵書で測ったが、書籍の題名・著者・本文はここに書かない（数字と抽象的な記述だけ）。

## 判定

| 課題 | GO の線 | 結果 |
| --- | --- | --- |
| A 関連箇所（20 か所、上位 5 件） | 14 か所以上 | **3 か所**（上位 3 件で採点、甘めに数えて） |
| B 意味検索（15 問、上位 10 件） | 10 問以上 | **0 問**（5 問流した時点で打ち切り） |

課題 B は 5 問すべてで、無関係な節が並んだ。しかも特定の 1 冊が上位を占め、
埋め込みの空間が退化しているときの典型的な形になった。そこで残りは流していない。

## 何が起きているか

**NLContextualEmbedding は文の埋め込みではない。** 文脈つきのトークン表現を返すもので、
検索のために学習されていない。トークンを平均して 1 本にまとめると、
向きが話題ではなく文章の長さと種類に引きずられる。

決定的だったのは次の測定である。

```text
同じ話題の長文どうし   0.683
別の話題の短文どうし   0.780
```

**長さが話題を上回る。** 単位の本文は中央 1,146 字（四分位 662〜2,325 字）で、
長さがまちまちである以上、順位は話題ではなく長さで決まってしまう。

短い文どうしでは、正しく順序が付く。

```text
所有権の説明 × メモリ解放の説明     0.619
所有権の説明 × 料理の説明           0.419   ○
```

つまりモデルが壊れているのではなく、**この使い方（長い節の代表ベクトルを作る）に向いていない。**

## 効かなかった手当て

| 手当て | 結果 |
| --- | --- |
| コーパスの平均を引く（中心化） | スコアの幅は 0.95〜0.98 → 0.40〜0.80 に広がるが、**順位は直らない** |
| 単位の長さを揃える（見出し＋冒頭 300 字だけを埋め込む） | **直らない。** 一部はむしろ悪化した |
| 単位を細かくする（章 → 節） | 節単位で測っている。粗さの問題ではない |

## 試せなかったもの

| | |
| --- | --- |
| `NLEmbedding.sentenceEmbedding`（文の類似度用） | **日本語に対応していない**（`nil` が返る） |
| Foundation Models（macOS 26） | 埋め込みの口を持たない。生成用であり、この機械では Apple Intelligence が無効で利用不可 |
| 変換した公開モデル（e5 系・Ruri 系） | **未実施。** PyTorch と coremltools の導入とモデルの変換が要る |

検索のために学習された公開モデルなら結果は大きく変わる見込みが高い。
ただしそれは「OS が配るモデルで済ませる」という前提（spec-local-ai.md 第 4.6 節）を捨てることであり、
モデルの同梱・配布・版管理という、この案が意識して避けた仕事が丸ごと戻ってくる。

## 運用の数字（品質と別に取れたもの）

蔵書 60 冊（EPUB 8 冊・PDF 52 冊）、6,107 単位。

| | |
| --- | --- |
| 単位の切り出し | 60 冊で 134 秒（PDF の本文取り出しが大半） |
| 埋め込み（本文全体、最大 12 窓の平均） | **138 ms/単位**。60 冊で 14 分 |
| 埋め込み（見出し＋冒頭 300 字） | **28 ms/単位**。60 冊で 3 分 |
| 索引の大きさ | 6,107 単位で **6.1 MB**（512 次元 float16） |
| 探索 | 6,107 単位の総当たりで **19〜22 ms**（問いの埋め込みを含む） |
| モデルの読み込み＋初回推論 | 27 ms |

読み取れること。

- **探索は速い。** 総当たりで足り、ANN は要らない（spec-local-ai.md 第 4.3 節の見込みどおり）
- **索引は小さい。** 1,000 冊でも 100 MB に収まる見当
- **作るのが重い。** 1,000 冊なら 4 時間（全文）／50 分（冒頭のみ）。
  優先順位・進み具合・中止が必須という見立ては正しかった
- 単位の切り出しは既存の道具で足りた。PDF 52 冊すべてがアウトラインを持っており、
  ページ窓で代える必要はなかった（**節の境界は取れる**）
- **1 単位が長すぎる。** 最長 141,717 字。窓 12 個で頭打ちにしているが、
  どのみち長い単位の代表ベクトルは意味を持たない

## これからどうするか

1. **意味の層は棚上げする。** spec-local-ai.md は案のまま置き、本編には取り込まない。
   Level 0 で完結しているので、棚上げしても失うものは無い
2. 再開する条件は **「検索のために学習された日本語対応の埋め込みモデルを、
   配布の仕事を含めて引き受ける」と決めたとき**。技術的な見込みはあるが、費用は案の想定より大きい
3. 再開するときは、この文書の運用の数字（単位の切り出し・索引の大きさ・探索の速さ）を
   そのまま使える。作り直しが要るのは埋め込みの段だけである

## 副産物

- **PDF のアウトラインは当てにできる。** 52 冊すべてで節の境界が取れた。
  意味の層と関係なく、節単位の見出し一覧や、検索結果に「どの節か」を添えるのに使える
- 単位の切り出しは既存の probe（`parse` / `text`）と PDFKit だけで書けた。
  新しい文書モデル（たたき台 §7）は要らなかった、という見立ての裏付けになる
