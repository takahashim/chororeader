# スパイクの結果：日本語技術書での意味検索の品質

spikes/local-ai-embedding.md を実施した。判定は **GO（条件つき）**。

検索のために学習されたモデル（Ruri v3）なら、関連箇所も意味検索も線を越える。
OS が配るモデル（NLContextualEmbedding）では届かない。

実蔵書で測ったが、書籍の題名・著者・本文はここに書かない（数字と抽象的な記述だけ）。

## 判定

蔵書 60 冊（EPUB 8 冊・PDF 52 冊）、6,107 単位。

| 課題 | GO の線 | NLContextualEmbedding | **Ruri v3 130m** | bekko a25m |
| --- | --- | --- | --- | --- |
| A 関連箇所（20 か所） | 14 か所 | 3 | **17** | 14 |
| B 意味検索（15 問） | 10 問 | 0（5 問で打ち切り） | **12** | 7 |

**Ruri v3 130m で両方が線を越えた。** 課題 A は上位 3 件、課題 B は上位 5 件で採点しており、
仕様書が定めた線（A は上位 5 件、B は上位 10 件）より厳しい条件である。

## モデルごとの違い

### NLContextualEmbedding（OS 配布）— 届かない

文脈つきのトークン表現を返すもので、**検索のために学習されていない。**
トークンを平均して 1 本にまとめると、向きが話題ではなく文章の長さに引きずられる。

```text
同じ話題の長文どうし   0.683
別の話題の短文どうし   0.780   ← 長さが話題を上回る
```

短文どうしなら正しく順序が付く（0.619 対 0.419）。壊れているのではなく、
長い節の代表ベクトルを作る用途に向いていない。
中心化（スコアの幅は 0.95〜0.98 → 0.40〜0.80 に広がる）も、
単位の長さを揃えることも、順位を直さなかった。

OS が配るものはこれで打ち止めである。`NLEmbedding.sentenceEmbedding` は日本語に対応しておらず
（`nil` が返る）、Foundation Models は埋め込みの口を持たない。

### Ruri v3 130m — 通る

日本語の文埋め込みとして学習されたモデル。512 次元。
検索用の接頭辞（`検索文書: ` / `検索クエリ: `）を持つ。

拾えた関連の例（主題だけ書く）。

```text
非同期処理の章   → 並行/並列の概念、await を待つ関数、スレッドセーフな設計
継承の節         → 別の言語の入門書の継承の章 3 つ
Docker の節      → 別の 2 冊の Docker 環境構築・インストール
テスト用ライブラリ → JUnit の章、別の言語のテストの章
確率密度関数     → 累積分布関数、連続型確率変数、連続変数の確率分布
```

外したものには傾向がある。**主題が数式や図表に寄った節**（材料工学の数値実験、
予測手法の比較）は、話題ではなく「数式が多い文章」という表層で寄る。

### bekko a25m — 課題 B で届かない

384 次元、多言語。ANE で **12 ms/単位**（Ruri の半分）と速く、索引も小さい。
課題 A は 14/20 で線に届くが、**課題 B が 7/15 で届かない。**

これは kohagi 自身の実測（`docs/coreml-publishing.md`）と整合する。

```text
                 JQaRA nDCG@10   JaCWIR MAP@10
ruri-v3-130m        0.7106          0.8584
bekko-a25m          0.5436          0.8843
```

JQaRA は知識に依存する検索、JaCWIR は Web 記事検索の指標である。
**技術書を横断して調べるのは前者に近い。** そこで差が付いた。

## 運用の数字

埋め込みは kohagi（Rust + Candle、`--device coreml` で ANE）で測った。

| | Ruri v3 130m | bekko a25m |
| --- | --- | --- |
| 埋め込み（ANE） | **22 ms/単位**（6,107 件で 2 分 18 秒） | 12 ms/単位（1 分 14 秒） |
| 埋め込み（CPU） | 110 ms/単位 | — |
| 索引（float16） | 6.1 MB（512 次元） | 4.6 MB（384 次元） |
| 512 トークンで切れた単位 | 41%（2,523/6,107） | 50%（3,071/6,107） |

- **探索は 0.35 ms**（6,107 単位の総当たり＋整列）。ANN は要らない
- **ANE が効く。** CPU の 5 分の 1。1,000 冊（10 万単位）でも 37 分の見当
- 単位の切り出しは 60 冊で 134 秒。既存の probe と PDFKit だけで書けた
- **PDF 52 冊すべてがアウトラインを持っていた。** ページ窓で代える必要はなかった

## 設計に効く発見

1. **モデルを同梱する話になる。** OS 配布では届かない以上、
   spec-local-ai.md 第 4.6 節（OS が配るモデルで済ませる）は捨てる。
   ただし kohagi が Hugging Face Hub から取って `~/Library/Caches/kohagi/coreml` に置く
   仕組みを持っているので、**アプリが配布・署名・版管理を全部背負う必要はない**
2. **埋め込みは別プロセスで足りる。** kohagi は JSONL を標準入出力でやり取りする CLI で、
   Swift から Process で呼べる。Core ML を Swift 側に持ち込まなくてよい
3. **単位の 4 割が 512 トークンで切れている。** 頭だけのベクトルになっている単位が 4 割ある。
   それでも線は越えたが、節をもっと細かく割るか、窓に割って平均するかは検討の余地がある
4. **接頭辞が要る。** Ruri v3 は文書側に `検索文書: `、問い側に `検索クエリ: ` を付ける。
   関連箇所（文書どうしの比較）では両方 `検索文書: ` で揃えた

## これから

1. spec-local-ai.md の第 4.6 節を書き換える（OS 配布 → Ruri v3 + kohagi）
2. 埋め込みの経路を決める。kohagi を同梱して Process で呼ぶのが素直
3. 単位の切り方（512 トークン超えの 4 割）をどうするか決める
4. 評価セットをこのスパイクのものから起こす。モデルや粗さを変えたら流し直す

## 副産物

- **PDF のアウトラインは当てにできる。** 52 冊すべてで節の境界が取れた。
  意味の層と関係なく、検索結果に「どの節か」を添えるのに使える
- 単位の切り出しに新しい文書モデル（たたき台 §7）は要らなかった、という見立ての裏付けになった
