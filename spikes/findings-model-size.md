# ruri-v3-30m で足りるか

spec-local-ai.md 第 4.6 節に「**`ruri-v3-30m` でも足りるかを測る**」と書いた宿題への答え。

結論から言うと **130m を既定にする。30m は選べるままにしておく。**
30m は合格線にちょうど乗るが、余裕が無い。しかも落ち方が悪い。

## 何を測ったか

手元の蔵書 60 冊（EPUB と PDF）から見出し単位で **6,107 単位**を切り出し、
同じ資料を両方のモデルで埋め込んで、同じ課題を解かせた。

- **課題 A（関連箇所）** 種を 20 か所選び、**別の本から**似た箇所を 3 件出す。
  上位 3 件に使えるものが 1 件でもあれば合格。合格線 14/20
- **課題 B（意味検索）** 問いを 15 本立て、上位 5 件を見る。合格線 10/15

種と問いは 130m のときと同じ選び方（乱数の種も同じ）。
本文・書名は一切書き出していない。数だけを持ち帰った。

## 結果

| | 130m | 30m | 合格線 |
|---|---|---|---|
| 課題 A（関連箇所） | **17/20** | **14/20** | 14/20 |
| 課題 B（意味検索） | **11/15** | **10/15** | 10/15 |

30m は**両方ともちょうど線の上**である。落ちてはいないが、余りが無い。

## 値段の側

30m の言い分はここにある。速さも容量も本当に効く。

| | 130m | 30m | |
|---|---|---|---|
| 配布物 | 264 MB | **78 MB** | 3.4 分の 1 |
| 次元 | 512 | **256** | 索引が半分 |
| 6,107 単位の埋め込み | 2 分 18 秒 | **44 秒** | 3.1 倍速い |
| 1 単位の推論（512） | 24.1 ms | **6.9 ms** | 3.5 倍速い |
| 問い 1 本（64） | 3.66 ms | **0.83 ms** | |
| 索引の大きさ（6,107 単位） | 12.5 MB | **6.3 MB** | |

## それでも 130m を採る理由

**速さは効く場所に効いていない。**
埋め込みは書籍を入れたときの 1 度きりで、裏で進む。1 冊あたり十数秒の差は待たされる時間ではない。
問い側の 3.66 ms は 0.83 ms との差が体感に出る値ではない。索引も 12.5 MB は本 1 冊より軽い。
つまり 30m が勝っている 3 つとも、**払っても痛くない値段**である。

**そして 30m の落ち方が、意味の層を入れる理由そのものを損なう。**
外した中身を見ると、語の重なりに引きずられている。

- 「システムプロンプトの設計」に対して**音響システム**の節を並べた（「システム」で寄った）
- 「空間計算量」に対して**巻末の索引ページ**を 2 件並べた（本文ではない紙面）
- 「データベースの索引が効かない」に対して、130m もやはり**巻末索引**を上位に出した

語の一致で寄る仕事なら、**すでにある bigram の索引の方が速くて正確**である
（spec.md 第 10 章）。意味の層に足したい価値は「語が違っても同じ話を見つける」ことにあり、
30m はそこが薄い。安いのは確かだが、安くなった分だけ**買いたかったものが減っている**。

## 差し替えは本当に容易だった

**実装は 1 行も変えずに 30m を読んだ。**

```
30m 読み込み 9120 ms / 256 次元 / 最大 512 トークン
```

次元は `config.json` の `hidden_size` から、平均の取り方は `1_Pooling/config.json` から読んでいるので、
置き場所を差し替えるだけで通る（`EmbeddingModel`）。トークナイザは 3 つの大きさで同一なので、
凍結した期待値もそのまま使える。

つまり **30m を選べる状態は、追加の実装なしに既に成立している**。
既定を 130m にしても、後から乗り換える道は塞がっていない。

## 落とし穴

- **`ruri-v3-30m` の Core ML 変換物は公開されていない**（ONNX 版は複数ある）。
  kohagi の `coreml-convert` に `--model-id cl-nagoya/ruri-v3-30m` を渡せば作れる
- 測り比べの符号で `"30" in "v130.jsonl"` が真になり、130m の問いを 30m のモデルで埋め込んでいた。
  次元が食い違って落ちたので気付けたが、**同じ次元どうしなら黙って混ざる**。
  モデルの名前で枝分かれさせるときは前方一致で見る

## 次

- 30m は**選べるが既定にしない**。spec-local-ai.md 第 4.6 節をそう直した
- 512 トークンを超える単位が 41%（2,523/6,107）ある。**切り方の方が効きそうである。**
  モデルを小さくするより、単位を適切に割る方が順位に効く可能性が高い。次はこちらを測る
