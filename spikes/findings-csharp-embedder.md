# C# で Ruri v3 の埋め込みが同じベクトルになるか

Windows 版に意味の層を入れられるかの後半。前半（トークナイザ）は
[findings-csharp-tokenizer.md](findings-csharp-tokenizer.md)。

トークナイザと同じで、**ずれても例外は出ず、黙って違うベクトルが出る**。
関連箇所も意味検索も静かに質が落ちるだけで、症状としては現れない。

## 実機は要らなかった

**正しさは実機では分からないし、実機でなくても分かる。**

実機でしか分からないのは速さと、native の依存が解決するかだけである。
ONNX Runtime には macOS 版があるので、**正しさは開発機で固まる**。
実機へ持っていくのは速さの測定だけでよい。

## 変換物

`ChoroConvert` に ONNX の出口を足した。

```sh
choro-convert --model-id cl-nagoya/ruri-v3-130m --out-dir <置き場所> --format onnx
```

| | |
|---|---|
| 出入口 | 入 `input_ids` / `attention_mask`（int64）、出 `token_embeddings` / `sentence_embedding`（fp16） |
| 大きさ | **253 MB**（fp16） |
| 軸 | batch も長さも動く |

Core ML 版と違ってバケットが要らない（長さが動く）ぶん、作りが小さい。
`tokenizer.json` は変換のときにそばへ写るので、アプリが要るものは 1 つの置き場所に揃う。

**長さに上限がある。** rope の表を最大長で焼いて切り出す作りなので、
`--max-sequence`（既定 2048）を越える入力は通らない。
アプリ側（`OnnxEmbedder.MaximumTokens`）が同じ長さで切り詰めるので届かないが、
**片方だけ変えると通らなくなる**。

## 結果

凍結済みの期待値 10 件（kohagi の `--device coreml` で作ったもの、例文は架空）に対して、
**10 件とも通った。**

| | cosine |
|---|---|
| 最良 | 0.999996 |
| 最悪 | **0.999977**（「短」の 1 文字） |
| 線 | 0.9999 |

短い本文ほど悪い。トークンが少ないぶん fp16 の丸めが出やすい。
それでも桁が 1 つ余っている。

## グラフに入っているものと、こちらの仕事

出口 `sentence_embedding` は**マスク付きの平均まで済んでいる**。
一方、元モデルは Transformer → Pooling の 2 段で **Normalize の段を持たない**。

| | どこ |
|---|---|
| マスク付きの平均 | グラフ |
| 接頭辞（`検索文書: ` / `検索クエリ: `） | `EmbeddingPipeline` |
| L2 正規化 | 同上 |
| 切り詰め | 同上 |

## 検査の組み方

**モデルが無くても噛む側と、本物が要る側を分けた。**
モデル一式は 250 MB あって CI には置けない。全部を本物に預けると、CI では誰も確かめていない。

| | 置き場所 | CI |
|---|---|---|
| 接頭辞・切り詰め・平均・正規化 | `EmbeddingPipeline`（Core） | **走る** |
| 参照実装との一致 | `OnnxEmbedderTests` | 飛ぶ |

3 通りに壊して、本物側の検査が噛むことを見た。

| 壊し方 | 落ちる検査 |
|---|---|
| 正規化をやめる | 単位ベクトルを返す |
| 接頭辞を取り違える | 参照実装と同じベクトル／文書と問いで違う向き |
| 接頭辞を付けない | 参照実装と同じベクトル／文書と問いで違う向き |

**正規化を外しても「参照実装と同じベクトル」は落ちない。**
cosine は大きさを見ないので、向きは同じままで通ってしまう。
macOS 版が「二つで補い合う」と書いているとおりで、こちらでもそのまま再現した。
**照合を 1 本だけ置いても防壁にならない。**

## まだ決めていないこと

- **配り方。** どこへ置いて、どう取らせるか。
  アプリはモデルの出どころを知らないので（決まった場所を見るだけ）、
  取る手順が足されるだけで使う側は変わらない
- **速さ。** Windows 機で測る。macOS 版は段落単位で 1 冊 6.4 秒
- **量子化。** int8 なら 127 MB まで落ちるが、**ベクトルが変わる**ので
  評価セットを流し直すまで「使える」とは言えない（spec-local-ai.md 4.3 と同じ筋）。
  fp16 の 253 MB は Core ML 変換物の 264 MB と同じ土俵なので、急ぐ理由は無い
